# Production speed audit — 14 October 2026

## Evidence and method

Production was serving `dba96cbc` at the start. The baseline hosted browser run is
https://github.com/DeHubToken/dehubweb/actions/runs/38505948000 . Its
`production-performance` artifact contains resource timings, long tasks, frame
samples and screenshots. These are single synthetic runs, not population percentiles.
Desktop uses Chromium at 1440×900; phone uses 393×852 with 4× CPU slowdown.
No artificial network throttling is applied. Warm means a second visit in the same
browser context. Feed-ready waits for the first visible author control; profile
navigation measures the profile shell, not completion of every profile request.

| Baseline | Feed ready | Profile shell | Back to feed | DOM nodes |
| --- | ---: | ---: | ---: | ---: |
| Desktop cold | 2,606 ms | 4,054 ms | 1,215 ms | 7,289 |
| Desktop warm | 1,506 ms | 3,373 ms | 1,277 ms | 7,355 |
| Phone cold, 4× CPU | 3,925 ms | 1,797 ms | 2,556 ms | 2,447 |
| Phone warm, 4× CPU | 3,073 ms | 1,810 ms | 2,694 ms | 2,416 |

Desktop scroll advanced 6,600 px. Its sampled p95 frame gaps were 300 ms cold and
267 ms warm, with maxima of 467 and 283 ms. Hosted Chromium rendering differs from
physical hardware, but these are substantial stalls worth investigating. The first
phone synthetic gesture did not move the feed, so its scroll frame results are
invalid. The harness now dispatches touch start/move/end and records scroll validity.

An authenticated desktop inspection also found approximately 8,800 DOM nodes and
28 video elements; element count alone does not establish active decoding.

## Confirmed avoidable work

1. **Badge warm-up bypassed the lazy boundary.** Commit `268d2c594` on 30 September
   scheduled `preloadBadgeShowcase` from the first metallic inline badge. That
   imports the showcase, prepares a hidden MetalStage and holds it for up to a
   minute. Production fetched `vendor-three` (678,407 decoded bytes) and
   `ShowcaseShell` (273,785 bytes) on both desktop and phone without a badge click.
   An idle callback does not make downloaded code, shader preparation or a renderer
   free. Remove mount-time warm-up; retain pointer, touch and keyboard intent.
2. **The default sidebar changed without changing its rendering budget.** Commit
   `d16c73a46` on 8 October made Chat the initial desktop panel. Hidden leaderboard
   and follow panels still mounted, while the 400px chat rendered its full message
   and buy-alert history, including old badges, links and media. Mount unused panels
   on first selection; render the most recent 30 chat items initially and preserve
   access to older rows through the existing translated load-older control.
3. **Preview playback budget did not cover loading.** `AutoplayVideo` limits a
   group to two playing tiles but attached a source to every visible tile. Source
   attachment now requires a playback slot too, avoiding losing tiles' metadata
   downloads. This applies to desktop and phone web.

These are demonstrated mechanisms and measured baseline costs. They do not prove
every reported slowdown has the same cause, or assign a percentage to each fix.

## Remaining opportunities

- AppLayout warms the entire composer and single-post route in an idle callback.
  Measure that dependency graph next; post cards already warm the post route on
  pointer intent. Preserve first-open responsiveness when changing this policy.
- The baseline includes roughly 600 KB decoded global CSS, 315 KB of English
  feature translations, and 100 KB of creator translations. Check feature-specific
  loading before raising bundle budgets. Decoded sizes are not network transfer sizes.
- Keep the recent feed-windowing and passive-touch fixes. They have already landed
  on live main; reverting them would reintroduce known deep-feed work.
- Extend measurements to authenticated sessions, Safari and physical phones,
  alternative themes and longer sessions before generalizing these timings.

## Native mobile parity

Native `BadgeArtwork` activates animation/showcase on interaction and has no idle
renderer warm-up. `LiveChatScreen` already uses FlatList with 30 initial rows.
The native Shorts carousel is also a FlatList. Preserve these properties rather
than porting DOM-specific fixes into native code. The companion mobile audit and
regression assertion document the shared startup budget. No native runtime change
or OTA is required for these web-specific fixes.

## Verification state

Changes are under review and cloud CI. A production after-measurement is required
after merge and publication; this baseline alone is not a verified speed improvement.
